## Summary

Establish one ChangeBudget-owned local HARD-authority foundation, bound to the physical Git common-directory instance, ChangeBudget-generated `work_id`/subject bindings, and exact canonical grants. G1 establishes physical-identity and trusted-context feasibility plus binding representation, without requiring persistent bindings; G2 is the first and only canonical registry/persistence for repository/work/subject bindings. Keep the registry outside the repository and the repo-local public reference opaque and non-authoritative. Direct grant create/revoke runs outside the supported governed Runtime Guard path under an explicit execution-boundary trust premise, not proof of human identity; each mutation and its audit use the same durable registry transaction. The existing Runtime Guard deterministically blocks supported governed grant create/revoke and reserved rebind before execution, regardless of generic host allow/always. Executable identity is used only for operation classification, not operator authentication. A descriptive subject label selected by the direct administrative operation is not a credential or identity proof; ChangeBudget generates canonical identifiers, and a first grant may create a new binding in that same registry transaction. A structured V2 metadata reference is only a locator/request descriptor and never an issuer or admin mechanism. Absent transport remains the Phase A result; invalid present reference blocks; a valid reference never upgrades Phase A to managed lifecycle ALLOW.

The Phase A plugin remains a read-only decision projection. Physical identity, trusted-context feasibility, canonical work/subject bindings, and durable storage have distinct trust obligations. No terminal/interactive signal, process ancestry, environment, executable identity, or `--actor` value is human proof. For pre-contract administration, a directly selected subject label is descriptive selection data only; ChangeBudget generates the canonical `work_id` and subject identifier as needed. G1 validates this source and binding representation without persisting it; G2 alone persists canonical bindings in the one registry. Agent prose or transport data cannot mint trusted work identity. Existing OpenCode V2 host fields do not authenticate an administrator or bind plugin location to every permission event, and Phase A forbids persistence in the permission hook; these are explicit boundaries, not assumed host capabilities. The design decisions and rejected alternatives are in [research.md](research.md); entity/validation rules are in [data-model.md](data-model.md); logical admin/transport contracts are in [contracts/admin-api.md](contracts/admin-api.md) and [contracts/authority-transport.md](contracts/authority-transport.md); future validation steps are in [quickstart.md](quickstart.md).

## Integrated Architecture

1. **Physical identity**: obtain Git common-dir to locate the ChangeBudget anchor; compare only a validated platform physical object identity. No path/remote/UUID/name/branch fallback.
2. **Trusted context**: G1 resolves active-contract context where available and establishes the source/representation for work and subject bindings without persisting them. For pre-contract administration, the direct operation requires a selected subject label as descriptive data only; ChangeBudget generates canonical opaque identifiers and does not infer EvoSpec semantics. Agent prose and transport data cannot supply trusted work identity. Work activation remains only a work-freshness concept. Direct execution outside the governed Runtime Guard path is an administrative trust premise, not authenticated human proof.
3. **Repository/work binding**: G2 creates the first and only canonical persisted repository/work/subject bindings in the strict user-local registry, resolving the opaque repo-local locator and verified physical identity. G3 may create a new work/subject binding together with the first grant in one registry transaction; no temporary registry or separate registration flow is required. `task_id` is correlation only.
4. **Durable transaction**: one cross-process lock and strict snapshot commit serialize canonical bindings, grants, replay/consumption state, and audit. Require file and containing-directory durability proof; never claim success from temp+rename alone.
5. **Canonical grant service**: validate immutable grant bounds and directly create/list/inspect/revoke through the provider-neutral admin contract. Each create/revoke and its audit commit in the same registry transaction; a first grant may add its binding in that same transaction, with no intermediate admin record. Enforce freshness and independent flags; listing/inspection never repair.
6. **Exact verifier/use boundary**: read-only `verifyGrant` compares bindings, operation/capability/path/ceilings, freshness, and lifecycle without audit writes, consumption, or `USE_ACCEPTED`. Distinct internal `authorizeUse` resolves fresh canonical context/IDs under the existing state -> contract -> registry lock order and revalidates all authority/context/lifecycle/revisions inside the commit. It durably records reusable-use evidence without consumption, or atomically commits one-shot consumption plus matching evidence in the existing registry/audit structure. A race has one winner maximum; ambiguous acknowledgement never returns `USE_ACCEPTED` or restores a possibly consumed grant. Downstream execution is outside G4.
7. **V2 adapter**: the bounded G5 implementation extends the existing Phase A classifier to block grant create/revoke and reserved rebind before execution on the supported governed-path verified shim, canonical Node, `npm exec`, and `npx` forms, regardless of host allow/always. Executable identity is used only to classify the operation. It parses only an existing opaque grant reference and bounded request metadata from the documented optional metadata record, derives operation facts from the correlated public session context and current running builtin edit, and calls only read-only `verifyGrant`. Absent preserves the Phase A decision; present invalid blocks; valid preserves Phase A action and does not enable managed lifecycle ALLOW. The permission hook remains read-only. This writer implementation is not native/G0/T027 acceptance and must not be relied on as HARD authority until the G0 FINAL, trusted-context, and out-of-hook audit/use gates pass. Unsupported routes and malicious same-user OS bypass are not claimed as covered.
8. **Acceptance and review**: run identity/durability/authority/transport/platform matrix, Phase A regression, full package/type/build/load checks, and independent security/correctness review. The narrow architecture review and bounded G3 review passed; the earlier Nox ten-file G1–G3 union was 97/97 (scoped historical evidence). Offline G4 is narrowly accepted on the previously G1/G2-qualified C: NTFS volume, including final independent Vera review and independent Nox pure-unit 7/7; this is not full T027 or native/HARD acceptance. The bounded non-authorizing G5 implementation's current independent Nox validation is 91/91 and final independent Vera review is PASS; formal T021–T023 acceptance remains blocked by the separate native G0 FINAL/trusted-context/out-of-hook-audit prerequisites. G0 FINAL/T017 remains **UNVERIFIED**; it is still required with accepted G4 and trusted-context/out-of-hook-audit proof before real OpenCode HARD integration. `tasks.md` and the terminal closeout record the evidence and boundaries.
