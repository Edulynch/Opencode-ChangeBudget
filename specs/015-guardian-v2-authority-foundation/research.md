## Decisions

### R-01 — Physical repository identity

**Decision.** Resolve Git's common directory only to locate a persistent ChangeBudget anchor, then ask a `PhysicalIdentityProvider` for the operating system's identity of that physical anchor. Bind the resulting stable volume/device and file-object identity (plus a trustworthy generation component where the platform supplies one) in the user-local registry. The repo-local public reference contains only an opaque registry locator. Neither the locator nor anchor contents establish identity or grant authority. Linked worktrees that resolve to the same physical common-directory anchor share a repository authority domain; work IDs remain distinct.

Preserve identity across a same-filesystem move only when the provider can prove the same physical object. A changed/missing anchor, changed common-directory object, copied/cloned repository, cross-machine copy, same-path replacement, uncertain identity generation, inaccessible identity API, reparse/symlink ambiguity, or unvalidated cloud/sync filesystem returns `UNAVAILABLE`/`MISMATCH` and denies HARD use. Do not fall back to path, remote URL, repository name, branch, copied UUID, or content digest. The provider must reject file IDs whose reuse/collision behavior is not sufficiently trustworthy; no equality promise is made for OneDrive until tested.

**Rationale.** This implements the selected common-directory physical-binding model, makes linked-worktree sharing explicit, and prevents descriptive or copyable repository data from becoming an identity proof.

**Alternatives rejected.** Canonical path, Git remote, repository name/branch, Git common-dir path text, or a UUID stored in copied repository content can collide or be copied and therefore cannot prove physical identity. A cryptographic federation or remote identity service is out of scope.

**Validation gate.** Separate Windows and POSIX providers must demonstrate stable object identity, same-filesystem move behavior, clone/copy distinction, replacement detection, file-ID reuse handling, and reparse/symlink rejection on each claimed filesystem. Until a provider passes, that platform/filesystem is unsupported for HARD authority. OneDrive is explicitly unsupported absent evidence.

### R-02 — Registry durability, transactions, audit, and replay state

**Decision.** Store a strict, versioned registry snapshot in a per-user local data directory outside the repository. This G2 registry is the first and only canonical persistence for repository/work/subject bindings, canonical grants, grant lifecycle/replay state, and append-only audit evidence; G1 establishes identity/context feasibility and binding representation without requiring persisted bindings or a temporary store. The repository contains only an opaque public reference and physical anchor, neither of which is a second canonical binding registry. Serialize every read-modify-write authority transaction behind a cross-process exclusive lock associated with the registry, with ownership metadata and conservative contention handling. A live, stale-but-unproven, malformed, or otherwise ambiguous lock is not broken automatically; recovery must be a separate explicit ChangeBudget operator action.

Commit a stable serialized snapshot by creating a same-directory temporary file, writing it, syncing the file, atomically replacing the registry, and syncing the parent directory where the platform/filesystem supports and proves that operation. Keep the lock until the full persistence barrier completes. If file sync, atomic replacement, directory sync, lock safety, or post-write validation is unsupported or fails, report no success and fail closed. No automatic migration of unknown registry versions is permitted. Direct grant create/revoke mutates the grant and records matching audit evidence in one locked snapshot commit; a first grant may create its new work/subject binding in that same G2 snapshot. No temporary/parallel binding store, separate registration workflow, or intermediate admin record is required. G4 separates strictly read-only `verifyGrant` (no audit, mutation, consumption, or `USE_ACCEPTED`) from internal durable `authorizeUse`. The latter resolves fresh canonical context under the existing state -> contract -> registry lock order, revalidates authority/context/lifecycle/revisions inside the commit, persists reusable-use evidence without consumption, or atomically commits one-shot consumption with matching use evidence. An ambiguous commit never returns `USE_ACCEPTED` and never restores a possibly consumed grant; downstream execution is outside G4.

**Rationale.** The repository already has stable JSON serialization, a temp-write/rename primitive, a state transaction lock, and a synced lock owner record. `src/core/state/state.ts` currently writes a temp JSON file and renames it without syncing the data file or containing directory. `src/core/state/lifecycle-lock-recovery.ts` syncs lock owner metadata and its recovery audit file, while its own comment explicitly notes that absent directory sync does not cover sudden power loss. These are useful patterns, not proof of the required registry durability guarantee.

**Alternatives rejected.** Separate grant, replay, and audit files introduce partial-commit windows; an in-repository grant database exposes authority-bearing state to copies; OpenCode plugin storage is not a ChangeBudget-owned authority registry; cloud/remote databases and dependencies violate the local-first/minimal architecture.

**Validation gate.** Inject failures at temp creation/write/file-sync/rename/directory-sync/lock and readback; verify read-only `verifyGrant` performs no writes and cannot return `USE_ACCEPTED`, while `authorizeUse` and create/revoke never report success without required durable state/evidence. Exercise process crashes before rename, after rename but before directory sync, and after durable consumption but before downstream completion. Test process-level concurrency and process restart. If a platform cannot prove the required barrier, it cannot issue or accept HARD grants there.

**Audit boundary decision.** The core provider-neutral authority service owns durable successful-use and administrative audit transactions. The Phase A OpenCode permission-evaluation hook remains read-only; it must not acquire authority by writing evidence or state. A hook-only preflight is not a successful authority use. The V2 transport's rejection/verification audit requirement is an explicit integration gate: no hook result may be treated as an audited verification or authority-bearing success until a ChangeBudget-owned audit path is demonstrated without adding hook side effects. In the absence of that path, the plugin may only preserve the existing Phase A result or block an invalid present reference; it may not claim the full audit acceptance criterion is met.

### R-03 — Trusted work/subject bindings and direct-administration trust boundary

**Decision.** G1 establishes the `WorkContextResolver` inputs, trusted-context feasibility, and logical work/subject binding representation; G1 does not persist canonical bindings. G2's single user-local registry is the first and only canonical persistence for repository/work/subject bindings. ChangeBudget generates an immutable opaque `work_id` for a work item or verified active-contract work activation and links the binding to coherent contract context where one exists, the verified repository, work-activation epoch, and authority/scope digest. For pre-contract administration, the direct ChangeBudget administrative operation requires an explicitly selected descriptive subject label. The label describes the intended beneficiary but is not a credential, identity proof, or canonical identifier; ChangeBudget generates the canonical `work_id` and subject identifier as needed. A first grant for a new work item may create and persist that binding in the same G2 registry transaction. No separate registration workflow, temporary registry, or EvoSpec-specific semantics are required. Contract ID is a local work handle only; it is not work identity proof. `task_id` remains optional correlation data only. Contract/work-activation/scope/authority changes invalidate grant freshness; normal Git HEAD changes do not. Work activation is a work-freshness concept, not an admin authorization object.

At verification, the exact subject must come from a ChangeBudget-owned subject binding; missing, ambiguous, or mismatched context blocks grant success. The current OpenCode host fields do not attest a human subject. A directly selected pre-contract subject label is descriptive selection data only, never proof or a canonical subject ID; ChangeBudget's generated binding is the trusted record. Agent prose, plugin metadata, `sessionID`, optional `agent`, environment variables, shell arguments, `task_id`, and a ChangeBudget reference cannot supply or mint the trusted binding. Direct grant administration outside the supported governed Runtime Guard path is an explicit execution-boundary trust premise, not cryptographic proof of a human. First-party executable recognition is used only to classify the supported operation; it does not authenticate the operator. TTY, process ancestry, environment, prompt, and `--actor` are not identity proof. Do not add a generic authentication/session/credential framework to resolve this boundary.

**Rationale.** The current plugin has session and agent identifiers but the official V2 contract does not attest a human subject or bind `ctx.location` to every received permission event. Existing Phase A first-party resolution proves only a narrow ChangeBudget executable/shim identity, not who initiated it. Existing contract IDs and task correlation values cannot replace generated work identity or ChangeBudget-owned subject binding.

**Alternatives rejected.** Using `contract_id`, `task_id`, session ID, agent label, first-party CLI identity, metadata, command-line actor text, TTY state, process ancestry, environment, or user prompt as trusted work/subject/admin proof would collapse correlation with authority and permit forged/stale context. A global account/login service or cryptographic human-presence system is outside the local-first specification.

**Validation gate.** G0 ENTRY must establish viable physical-identity and trusted-context sources/representation, storage feasibility, and the supported governed-path classifier/deny behavior before G1/G2; it does not require or prove persisted bindings. G1 verifies identity/context feasibility and representation without persistence. G2 must demonstrate that the single registry is the first and only canonical persistence for repository/work/subject bindings. G0 FINAL must prove real direct create/revoke and atomic mutation/audit only after G1/G2/G3 exist, including any first binding created with its grant in one transaction. Neither G0 gate proves human presence. Unsupported routes and malicious same-user OS bypass are outside the protection claim. If required bindings or the supported boundary are unavailable, fail closed.

### R-04 — Grant scope, path rules, ceilings, freshness, and state transitions

**Decision.** Canonical grants are immutable in their bounds and strict in schema/version. Each binds a grant ID; repository binding/reference; `authority_id`; `work_id`; subject; operation and capability set; canonical path scope; numeric ceilings; independent `allow_new_files`, dependency, migration, configuration, and public-API permissions; validity window; governing authority revision/digest; issuer/provenance; and lifecycle/consumption state. Canonical relative paths use `/`, are normalized once, reject traversal/ambiguous roots/symlink escapes, honor deny rules before allows, and never authorize protected `.changebudget/**`. Reuse the existing contract path-pattern semantics rather than adding a second wildcard language. A covered existing path does not imply a new-file permission; each sensitive permission is independent.

For numeric bounds, verify the requested operation against the grant ceiling without replacing the request's narrower values: a request for 18 under a ceiling of 60 remains a request for 18. Freshness is bound to the current coherent contract/scope, work-activation epoch, authority epoch, and repository binding, not routine commits/HEAD movement. `REUSABLE` grants remain `ACTIVE` until expiry, revocation, or freshness failure. `ONE_SHOT` permits exactly one audited successful use (`ACTIVE -> CONSUMED`). Revocation is `ACTIVE -> REVOKED`; `CONSUMED` and `REVOKED` are terminal and durable. Expiry is evaluated deterministically from stored validity and does not silently rewrite persisted data during inspection.

**Rationale.** Independent capability bits avoid implicit widening, immutable requests preserve human intent, and freshness invalidates genuinely changed governing authority without treating ordinary repository progress as revocation.

**Alternatives rejected.** Copying the grant ceiling into the request widens the request; tying freshness to each Git HEAD would revoke on ordinary commits; reusing contract/task IDs as work IDs merges distinct work activations; auto-rewriting corrupt/expired state during inspection hides evidence; shared path/prefix string checks admit sibling collisions.

**Validation gate.** Exhaustively test exact/narrower/over-ceiling requests, all independent flags, exact paths, traversal, prefix siblings, case rules, new files, denied/protected paths, stale/revoked/expired/malformed/cross-binding requests, stable digest encoding, and the “18 remains 18 under 60” example.

### R-05 — Provider-neutral admin surface and structured OpenCode V2 transport

**Decision.** Keep grant policy and persistence behind a focused ChangeBudget authority service. Define logical direct create/revoke, list/inspect, and audited verification operations; do not lock a CLI spelling or expose persistence internals as a public API. Direct execution outside the supported governed Runtime Guard path is the administrative trust premise, not human-identity proof. A descriptive subject label selected by that operation is not a credential or identity proof; ChangeBudget generates canonical identifiers, with any first work/subject binding committed alongside its first grant in the sole registry transaction. This does not require or imply a terminal, prompt, process ancestry, environment, executable identity, or cryptographic human proof. Listing/inspection are state-read-only and must not repair malformed state.

Use only the documented OpenCode V2 permission-evaluation hook as the current governed interception boundary. Extend the existing ChangeBudget command classifier to block grant create, grant revoke, and reserved rebind before execution for supported verified shim, canonical Node, `npm exec`, and `npx` forms. Existing Phase A source recognizes bounded executable identities, but does not implement this grant-admin classification; executable identity is only an operation-classification input, not operator authentication. Ambiguous routes within the supported boundary fail closed. Unsupported routes outside that boundary and malicious same-user OS bypass are not claimed as protected. Denial is unconditional for supported governed mutation paths even when a grant ID is known or host permission is `allow`/saved `always`. The optional V2 `metadata` field may contain only a versioned ChangeBudget-namespaced opaque existing grant reference and bounded requested-operation metadata; it does not carry an admin authorization object. Derive repository, work, subject, authority, and freshness locally. Compare bounded request details to actual intercepted action/resources and canonical grant; never accept caller-supplied identity fields as proof. Absent reference is a pure pass-through to Phase A. A present malformed, unknown, stale, revoked, replayed, mismatched, or unresolvable reference is invalid and blocks; it is never treated as absent. A valid reference does not change the Phase A action in this batch and cannot produce managed START/AMEND/CLOSE ALLOW. Preserve more restrictive incoming host effects. A configured explicit host deny does not invoke the plugin hook and remains final. Even after offline G4 acceptance, no later real OpenCode HARD integration may rely on the reference until G0 FINAL, trusted context, and an out-of-hook audit path are also accepted.

**Rationale.** The existing plugin registers `session.context` and `permission.evaluate`, reads optional application metadata, computes its own action projection, preserves incoming restrictive effects, and denies intercepted evaluation failures. Existing `classifyChangeBudgetArguments` has no authority-admin command schema; the existing first-party resolver can recognize only bounded shim/direct Node/npm-exec/npx identities and does not establish operator identity. Official V2 docs identify plugin location as plugin-instance context and show permission metadata as an open record; neither makes those values authenticated. The plugin's current ASK projection and strict Permission API vocabulary remain the compatibility baseline; this batch adds no host APIs or lifecycle grants.

**Alternatives rejected.** Inventing native OpenCode fields for trusted subject/work identity; interpreting `ctx.location.project.canonical`, saved `allow`/`always`, `ask`/`once`, event `agent`, TTY/interactivity, process ancestry, environment, first-party executable identity, or arbitrary metadata as operator authentication; adding a separate human-presence gate, generic auth/session/credential framework, session permission rules, a V1 adapter, an EvoSpec bridge, or a plugin-owned grant issuer; claiming protection for unsupported execution routes or malicious same-user OS bypass.

**Validation gate.** Use actual documented host event fields and existing metadata only. Add classifier/runtime negative tests for each supported shim/Node/npm-exec/npx form, including grant create/revoke/reserved rebind with known grant IDs and generic allow/always; ambiguous supported routes must fail closed. Confirm event serialization and subject sourcing against an installed V2 runtime before relying on any value. Prove the read-only-hook/audit boundary described under R-02. If proof is absent, do not report transport conformance or authority-enabled operation.

### R-07 — Separate permissive identity from denial-only admin intent

**Decision.** Preserve the existing first-party identity resolver and all of its executable/interpreter attestations as the only basis for any permissive ChangeBudget classification. Do not add a Node anchor, executable registry, persisted fingerprint, operator configuration, or other trust source. A distinct read-only `DenyOnlyAdminIntent` path can classify only a recognized grant-create, grant-revoke, or reserved-rebind request for the verified canonical ChangeBudget CLI into the existing unconditional governed-admin DENY; it never returns or synthesizes first-party identity and never inspects or mutates authority state.
