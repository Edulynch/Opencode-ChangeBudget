# Contract: OpenCode V2 Plugin Hooks

> Status: Draft — **NEEDS_CLARIFICATION**. The official V2 material inspected does not verify the proposed installed permission-evaluate hook/effect contract or an authenticated human issuer; local repository binding is also unverified. This contract records product constraints and source hypotheses, not installed-host behavior, an implementation baseline, or completed Guardian V2 behavior.

## Scope

The source currently proposes a native V2 plugin with id `changebudget` and exactly two registrations:

- `ctx.session.hook('context', callback)`
- `ctx.permission.hook('evaluate', callback)`

This is an inspection of the proposed source shape, not a verified promise that the pinned installed host supports or invokes both registrations as needed. Do not introduce tool/command pre-execution adapters, server callbacks, correlation maps, compatibility transports, or substitute host APIs to close that evidence gap.

## Session Context

The source context callback proposes appending deterministic ChangeBudget text to a mutable outgoing model context. Official V2 docs describe the `context` hook as modifying the outgoing model call, not persisted history; it is not a trusted record of the human's original admission or a way to reject it. The docs say `ctx.location` identifies where the plugin instance is loaded, not every session it can access. Neither context text nor plugin location authenticates intent or binds an operation to a repository. Actual installed behavior remains a gate.

## Permission Evaluation

The current source assumes an evaluate callback receives `sessionID`, `action`, `resources`, optional metadata, and mutable `effect`/`message` fields. The official V2 plugin page documents generic/session hooks and `ctx.permission.list/get/reply`, but does not document `ctx.permission.hook('evaluate')`, this event shape, effect/message mutation, invocation order, or coverage of all operations. Pinned installed `@opencode/plugin` declarations were unavailable in the bounded inspection. Treat every item below as provisional until the actual installed host and package declarations are verified.

If and only if the installed-host gate confirms this hook, the proposed evaluation would:

1. normalizes the operation and target context;
2. recognizes supported ChangeBudget CLI forms only after executable and full argument-grammar classification;
3. evaluates existing ChangeBudget state and active contract policy without redefining SPEC-002/003 decisions;
4. treat `materialDecision` only as an existing optional input, never as issuer proof or grant evidence;
5. projects `allow`, `ask`, or internal `block` with a stable rule; and
6. aggregates all results as `deny > ask > allow`.

The product rules constraining a future projection are resolved in `spec.md`: preserve the direct explicit outcome; distinguish advisory expected estimates from provenance-qualified hard ceilings; use only current or verified bounded grant authority; continue with the minimum covered delta; refocus an optional oversized proposal only when optionality is independently verified; ask only for minimum materially new authority; and block invalid/unsafe/protected/actual-force-without-fresh-approval/unknown work. An untrusted or absent optionality hint does not prevent a concrete operation already covered by authority from continuing. A category, `REPAIR`, path mismatch, or recognized CLI class alone does not trigger a blanket ask/block. MVP scope/deferrals are as specified in `spec.md`; cloud/distributed authorization, arbitrary third-party issuers, organization grants, cryptographic federation, and LLM compliance as enforcement authority are deferred. No new hook/API/schema or REFOCUS permission effect is defined here. Existing source projection is old-behavior evidence, not an implementation claim.

Internal `block` is emitted as V2 effect `deny`. Once the evaluate callback is registered and invoked, it preserves an incoming `deny` and denies a potentially mutating intercepted operation if evaluation fails. This says nothing about requests that cannot reach an unregistered hook.

## Official V2 Documentation Boundary and Conditional Approval Handling

- [Build plugins](https://opencode.ai/v2/docs/build/plugins) documents generic hooks and examples for session `prompt` and `context`. A prompt hook transforms the draft into canonical persisted input and the docs explicitly state it exposes no typed rejection API; it runs at admission, not before every model call. It is not, by itself, proof that an authenticated human approved a structured grant. The session `context` hook changes only outgoing model calls, not saved history. `ctx.location` is the plugin instance location, not every session's location. The same page documents `ctx.permission.list/get/reply` for inspecting/resolving pending requests, but not an evaluate hook with a mutable permission effect/message.
- [Permissions](https://opencode.ai/v2/docs/permissions) documents `allow`, `ask`, and `deny`, with deny dominating ask/allow when operations check multiple resources. A client can answer an ask with `once`, `always`, or `reject`; `always` saves the tool's proposed pattern as a durable project-scoped allow rule. That saved rule is host convenience, not a ChangeBudget grant. Guardian must independently re-evaluate every covered operation; `always` cannot satisfy provenance, expand a grant, bypass operation-level evaluation, or override configured deny. Never represent a saved rule as the authenticated human issuer event.
- Consequently, ASK can establish a grant only after a supported channel is proven to bind a fresh human choice to the exact ChangeBudget operation/scope and retain it in the ChangeBudget-owned lifecycle transaction. An ordinary host `once` approval proves at most permission for that pending host request; `always` persists broader permission state and is expressly not authority. If the installed host offers no trustworthy bounded approval event, do not infer one from prose, callback metadata, or session context: surface the integration/approval path as unavailable or block.
- Force-close/bypass has a two-stage preflight: request approval for the exact single force operation through that verified channel, and do not execute the pending attempt until the fresh event is validated and retained. Rejection, stale approval, or an unavailable/unverified channel blocks the attempted operation or makes the integration unavailable. A generic host `ask`/`once` reply does not by itself prove the human issuer event, and a saved `always` rule can never stand in for force approval. Even a verified force approval never authorizes direct `.changebudget/**` writes.
- REFOCUS is not a V2 effect or authority update. The proposal is to deny only the optional proposed mutation with structured reason/feedback, and optionally place advisory next-request guidance in outgoing session context. Context text cannot undo a denied operation, establish optionality, or authorize the next request. Both the user-facing feedback path and denial effect must be verified on the installed host.
- Any incoming `deny` remains `deny`. Evaluate every resource independently and aggregate deny before ask before allow. A partial resource list, mixed allowed/denied paths, unresolved target, or out-of-repository target cannot be treated as covered. This aggregation is a required acceptance behavior, not proof the proposed hook receives all resources.

## Hook Availability and Failure Modes

- The plugin is optional. If absent or disabled, core ChangeBudget CLI behavior remains available, but SPEC-004 provides no OpenCode interception guarantee.
- If setup or permission-hook registration fails before the `evaluate` callback is registered, mutations may not be intercepted and cannot be described as blocked by this runtime guard. The integration must be surfaced as unavailable through supported host/integration feedback; selecting the concrete feedback mechanism is implementation/validation work. Do not add an API or schema here.
- If the evaluate callback is registered, invoked, and evaluation fails for a potentially mutating request, it MUST return `deny` for that intercepted request through the supported permission path (FR-014). The current source callback has a catch that assigns `deny`; this is source inspection, not host-test evidence.
- This distinction is a workflow-guard availability statement, not a sandbox guarantee or a claim that all mutations are intercepted.
- Installed-host verification is a blocking dependency, not merely a final smoke test: confirm plugin/package versions, exact registered hook support, dispatch timing/resource completeness, observable effect/message semantics, and supported failure feedback. A source mock or fixture cannot establish this contract.

## Passive Mode, CLI Operations, and Protected State

- Ordinary non-ChangeBudget operations without active ChangeBudget context remain passive/allowed, subject to fail-closed classification and the direct-state rule below.
- ChangeBudget CLI recognition requires a supported executable form and complete grammar; absolute executable paths require verified installed-package shim identity. Recognition classifies an invocation but does not itself grant authority or determine runtime action.
- The prior requirement that every recognized managed CLI mutation (including `init`), external `update`, and `close --force` receive a one-operation ask is **OBSOLETE - REQUIRES REVISION**. Product lifecycle conditions are resolved in `spec.md`: clean first-time `init` only in an eligible repo with no conflicting state or protected/pre-existing overwrite conflict, when covered by an authenticated direct setup request or verified parent premise (no separate exact-init request); narrow `start` covered by premise/grant; minimum grant-covered `amend`; normal close after PASS and required completion conditions; force-close preflight may ask only for exact fresh approval through a verified human channel and blocks actual execution without it; autonomous read-only `integrate opencode --dry-run` and `update --check`; proven-owned wrapper refresh; explicit human setup/integration request for real integration; explicit user update request for a real package update. Direct `.changebudget/**` writes remain blocked regardless. Exact existing-input-to-hook projection is implementation planning, not unresolved product direction.
- The previous automatic `ask` for every out-of-scope path or disabled sensitive-category match is also **OBSOLETE - REQUIRES REVISION**. Such a signal alone does not distinguish current authority, optional work to REFOCUS, and genuinely new authority. A premise explicitly requesting sensitive-category work does not trigger redundant consent solely by category; novel expansion is authority-evaluated. Preserve SPEC-002 allow-list/hard-deny ownership and direct protected-path gates.
- **PENDING SOURCE DIVERGENCE:** the currently injected `index.ts:38-56` session text requires developer-approved paths/budget before `start`, says "Never widen or amend a contract automatically. Ask the developer for explicit approval of each exact path and reason," and says to close only after validation and developer agreement. The amendment and close requirements conflict with conditional autonomy for minimally covered `amend` and normal `close` after `PASS`. The start instruction conflicts where it asks again for paths/budget already covered by the human premise or valid grant; source reconciliation is pending, not a product ambiguity. The injected text has not been updated or verified by this documentation task; its eventual revision and runtime evidence remain pending. The same source directs running relevant targeted tests/types/lint/builds; that is task-relevant validation, not permission to add optional tests or unrequested infrastructure.
- Prior read-only classifier examples are `status`, `diagnose`, help/version, `check` without satisfaction evidence, `update --check`, and `integrate opencode --dry-run`; they are evidence about static grammar, not a universal host behavior claim. The beta.7 host discrepancy remains unresolved.
- Unknown/malformed command forms, invalid satisfaction evidence, shell control operators around an attempted ChangeBudget invocation, and unrecognized wrappers for such an invocation fail closed in every repository state. Absolute executable paths require verification as shims for the installed ChangeBudget package; matching a name/string is insufficient. This does not promise support for every Windows wrapper.
- A direct mutation targeting `.changebudget/**` is blocked in every repository state, including before initialization. CLI recognition never authorizes direct file/edit, shell, or Git writes to the protected path.
- For the Git scanner, #36/beta.6 source/test evidence covers only supported read-only forms: `git ls-files`, `git check-ignore`, and `git status` pathspecs, including supported split-resource variants. Every sibling resource is evaluated; a mutation or unknown resource cannot inherit a read-only result. This evidence is not a universal host scanner guarantee.
- Preserve the direct explicit human premise's exact outcome and minimize implementation/authority delta, not the outcome. Use sequence: premise; within-current-authority continue; mechanically implied minimum concrete delta; minimum valid-grant-covered delta; REFOCUS only when optionality is separately verified (otherwise a covered operation continues); ASK for minimum materially new authority; BLOCK invalid/unsafe/protected/actual-force-without-fresh-approval/unknown. “Reject the oversized solution, not the task.” “Refocus before escalation.” “Minimize implementation expansion, never the user's requested outcome.” “ChangeBudget asks for new authority, not repeated consent for authority the human already granted.” A soft expected estimate overrun alone is not ASK/BLOCK. Hard ceilings require verifiable exact human/policy provenance; unresolved legacy provenance is HUMAN_REVIEW when classification is necessary, and Guardian BLOCKS operations relying on it. See SPEC-002 `spec.md` FR-021 and SPEC-003 `spec.md` FR-002/FR-003/FR-004/FR-007. REFOCUS is a workflow concept, not a hook action/command/exit code/enum/state/API/schema.
- `REPAIR` alone neither blocks nor authorizes: current-authority repair continues with minimum delta; valid covered amendments continue with minimum delta; independently verified optional work may refocus; new authority asks; invalid/unsafe blocks. Untrusted/absent optionality is not a reason to block work already covered. `HUMAN_REVIEW` reasons distinguish verified optional→REFOCUS, new authority→ASK, invalid/unsafe authorization/state→BLOCK. Do not invent final reason codes or map one old reason to all outcomes.
- Authority distinguishes trusted human intent, ChangeBudget-canonical structured grant, and verified human authorization event. Orchestrator is consumer/reference, not issuer; prefer grant id/reference without specifying shape. Bind repo identity, work/task identity, authority/schema version, and lifecycle status. Malformed/forged/cross-repo/cross-task/revoked/expired/consumed/stale grants block, not ask. Valid bounded START→AMEND→REPAIR→CLOSE reuse is permitted; after successful CLOSE, no unrelated future replay. These are product requirements, not a claim the hook presently performs these checks.
- Retain ChangeBudget-owned structured evidence for each autonomous authority-consuming lifecycle operation: requested operation, current authority, grant/premise coverage, minimal delta, subset/boundary checks, no-prompt rationale, and any REFOCUS/ASK/BLOCK decision and reason. This supersedes the historical no-audit clarification for MVP. It does not prescribe a store or make permission-hook evaluation persist evidence; current source is not claimed to do so.

## Determinism and Side Effects

For identical verified repository state, operation input, and validated evidence, the deterministic policy result is identical. Permission evaluation itself must not amend contracts, persist approvals, change `.changebudget/**`, or call external services. **PENDING SOURCE DIVERGENCE:** current `opencode-plugin/src/evaluator.ts` invokes `evaluateAndRecordMaterialDecisionInPlace` for a valid `materialDecision`, which can persist a ledger during permission evaluation and conflicts with SPEC-004 FR-017. This docs-only task does not fix it; the later source plan must remove/rehome this side effect under ChangeBudget-owned lifecycle handling before claiming conformance.

If the resolved mapping selects `ask`, it applies to one operation only, does not amend contracts, persist approval, or authorize another invocation. This conditional ask behavior does not preserve the obsolete universal CLI ask rule. The plugin permission hook itself does not write `.changebudget/**`; recognized ChangeBudget lifecycle commands remain distinct and must obey their conditions. Pre-initialization direct-state and some unresolved/unrecognized-wrapper behavior are known to be inconsistent with the current projection source and remain PENDING; this contract does not imply those implementation gaps are resolved. See `tasks.md` and `research.md` for coverage locations, aligned owner semantics and implementation-representation planning, and host-evidence status.
