## Decisions

### Native plugin shape

The source proposes `Plugin.define({ id: 'changebudget', setup(ctx) })`; the official V2 guide demonstrates `Plugin.define` generally. This does not validate every source registration against the installed pinned package/host. No older API shape is recognized or translated.

### Hook surface

The source proposes `ctx.session.hook('context', ...)` and `ctx.permission.hook('evaluate', ...)`. Official docs describe session context hooks and generic hooks but do not document the proposed permission-evaluate hook/event/effect contract. Whether it receives every action/resource before execution is an implementation acceptance question; do not assume it from a source call or fixture. No supplemental adapter, pre-execution hook, or correlation map is authorized as a workaround.

### Restrictive aggregation

Project each resource independently, then select the strictest result. The order is `deny > ask > allow`; internal `block` becomes V2 effect `deny`. An incoming restrictive effect is never weakened.

### Unknown and broken context

An uninitialized repository is passive for ordinary non-ChangeBudget operations, subject to the all-state direct `.changebudget/**` block and fail-closed attempted-CLI classification clarified below. An initialized repository with missing/corrupt state, no active contract, or an unresolved mutation target fails safe with a denial. Read-only work remains allowed when it can be classified as read-only.

### Structured material decisions

Existing material-decision input is an explicit structured value that current source reads from permission metadata, normalizes, and passes to existing execution-gate governance. Current source can observe that this particular metadata value is `ABSENT`; that absence MUST NOT be treated as proof that no human premise or ChangeBudget-canonical grant exists. Do not invent an assumption that canonical grant evidence is always present in this metadata slot, or that prose/transport alone issues a grant. No ordinary request fabricates a material proposal. The product constraint is that permission-hook evaluation must not persist approvals or lifecycle evidence; current source has a valid-material-decision path that may persist a governance ledger, recorded below as a PENDING divergence from that constraint. Authority provenance and requirements are planning design and no new metadata shape is proposed.

### Local-first behavior

The intended integration reads local state and makes no network calls or plugin-owned permission-hook writes; lifecycle evidence belongs to ChangeBudget-owned lifecycle handling. Current source's material-decision path may write a governance ledger during evaluation, so the no-hook-write invariant is not currently met. The core CLI remains independent when the plugin is unavailable.

## Clarification and traceability (2026-09-24)

### Prior #41 CLI projection — historical and obsolete as a universal ask rule

The user direction keeps a distinction between direct state mutation and recognized ChangeBudget CLI lifecycle operations, but the earlier one-ask-per-recognized-mutation projection is **OBSOLETE — REQUIRES REVISION**. #41/beta.7 is historical evidence of a static classifier and its previous asks, not a Guardian V2 policy approval or implementation.

- Direct writes to `.changebudget/**` remain blocked in every repository state, including before initialization and with no active contract.
- The historical classifier handled lifecycle forms only through recognized ChangeBudget CLI invocations; recognition is not authority. Final routine autonomy also includes localized requested task-surface edits, relevant tests, and mechanical changes, subject to current bounded authority. `start`, minimum covered `amend`, normal `close` after `PASS`, and other lifecycle cases follow `spec.md`; this is not a claim of current runtime effects or conformance.
- The prior static classifier called `init`, `start`, `amend`, `close`, non-dry-run `integrate`, satisfaction-evidence `check`, external `update`, and `close --force` mutating CLI forms. Its former universal ask mapping is not binding. Product conditions for these lifecycle cases are resolved in `spec.md`; exact existing-input-to-runtime projection is planning design.
- The former read-only examples were `status`, `diagnose`, help/version, `check` without satisfaction evidence, `update --check`, and `integrate opencode --dry-run`. These are classifier examples, not proof of consistent host behavior; preserve the beta.7 discrepancy below.
- Unknown/malformed CLI syntax, invalid evidence, shell control operators around an attempted ChangeBudget invocation, and unrecognized wrappers for such an invocation remain fail-closed requirements in every repository state. Absolute executable paths require verified identity as a shim for the installed ChangeBudget package; a name/string match alone is insufficient. This is not a claim that every Windows wrapper is supported.
- A host `ask` concerns a pending operational permission request; a response may be `once`, `always`, or `reject` under host behavior. None establishes ChangeBudget authority, authorizes direct `.changebudget/**` edits, or persists/widens ChangeBudget policy. This does not preserve the obsolete ask-per-operation trigger.

The current projection source does not fully meet the direct-state requirement: `opencode-plugin/src/projection.ts` returns passive allow at approximately lines 88-95 before checking `targetInChangeBudget` at approximately lines 156-163. Thus a direct state mutation can be allowed before initialization. The same early passive return precedes unresolved-mutation handling for ordinary operation classes; some malformed/unrecognized wrapper forms for an attempted ChangeBudget invocation may therefore avoid the requested fail-closed result before initialization unless they were recognized specifically as `changebudget-unsupported`. The all-state direct-state prohibition and unknown attempted-CLI fail-closed requirement remain normative; these source-order mismatches are implementation gaps, not policy exceptions, and are PENDING remediation and regression evidence. Re-scope follow-up to the resolved Guardian V2 sequence; do not apply the obsolete broad ask/block projection.

### Guardian V2 product and cross-spec audit (2026-09-24)

- Preserve the exact direct-human requested outcome, including Docker + Redis Cluster + three instances. Minimize optional implementation delta, not the goal; do not add optional tests/refactors/infrastructure. REFOCUS rejects an oversized solution, not the task, and precedes escalation; it is a workflow concept, not runtime action, command, exit code, API, or schema.
- Soft planner/agent `expected_files`/`expected_changed_lines` concepts warn of drift and alone do not ask or block. `max_files`/`max_changed_lines` are hard only with verifiable human/policy provenance; exceeding a qualified hard ceiling needs new authority. SPEC-002 FR-021 preserves deterministic legacy classification: exact human ceiling intent or trusted exact policy provenance is HARD; a verifiable unadopted recommendation is SOFT; unknown/ambiguous origin or intent is UNRESOLVED. SPEC-002 FR-011/FR-012 remain authoritative for allow-list and hard-deny semantics.
- `REPAIR` alone is not a stop or authority grant. Continue within current authority or a valid covered minimum; REFOCUS only independently verified optional work. An absent/untrusted optionality hint does not stop a covered operation. `HUMAN_REVIEW` is a check result, not authority. Authority-delta minimality remains 18→19 rather than 18→60, and exact `src/foo.ts` rather than `src/**` when sufficient.
- Preserve the exact premise separately from a ChangeBudget-canonical grant. Only the orchestrator receives the canonical grant identifier/reference; agent-facing work uses exact bounded instructions. Grant evidence binds exact paths, capabilities, ceilings, authority/schema version, lifecycle, work/repository, and provenance. No command name, schema, public API, or numeric default is selected here.
- The selected model is **CHANGEBUDGET_NATIVE_APPROVAL_REQUIRED**. Agent-invoked ChangeBudget administration through the guarded Runtime Guard path that creates, expands, revokes, or rebinds authority MUST BLOCK regardless of saved `always`/allow rules. The agent may prepare a minimum proposal and user-facing instructions; a human performs the ChangeBudget-owned admin action outside governed agent execution. Ordinary OpenCode `ask` is operational only and never creates canonical HARD authority. Genuine new HARD authority produces a minimum proposal and a runtime BLOCK pending that separate native action; this user-facing request/proposal is not a runtime `ask`.
- Repository binding uses a user-owned registry outside the repository, a repo-local public reference, and a physical ChangeBudget anchor associated with Git common-dir. Linked worktrees sharing the common-dir share the local repository authority domain, while grants remain work-bound. A genuine unavailable/unreliable physical ID means HARD binding fails closed; routine non-HARD work may continue. There is no path, remote, or copied-UUID fallback. An unchanged common-dir instance remains the same instance despite changed working contents; Git baseline/contract rules handle content. Same-path replacement is a new instance only when the Git common-dir instance changes. Moves preserve authority only with verified physical identity; clone/full-copy/cross-machine does not inherit HARD authority. Rebind is an explicit human action, audited with old/new binding, and does not silently migrate grants.
- Threat boundary excludes a malicious unrestricted same-user OS actor tampering with external/repo/anchor/admin paths; the design adds no cryptographic federation or OS sandbox. Routine autonomy is limited to clean eligible init, narrow start, localized requested task-surface edits/relevant tests/mechanical changes, within-authority repair, minimum covered amend, and close after PASS/required completion. No implicit protected or unrequested dependency, migration, config, API, force, unrelated-root, or administrative authority.
- ChangeBudget-owned lifecycle evidence remains required for autonomous authority-consuming operations and every native grant administration action (create/expand/revoke/rebind). The external registry is local user-owned state, not a cloud/global grant database. Permission-hook evaluation must not persist that evidence. These are finalized product decisions; implementation representation and recovery details remain design/validation work.

MVP includes provenance, covered lifecycle operations, canonical grants, local registry/reference/physical-anchor binding, rebind audit, and structured evidence. Defer cloud/distributed authorization, arbitrary third-party issuers, organization grants, cryptographic federation, OS sandboxing, and LLM compliance as enforcement authority. Planning status is READY_FOR_TASKS only; it does not imply implementation or host/filesystem conformance.

### Hook availability versus evaluation failure — source inspection only

- In `opencode-plugin/src/index.ts:730-742`, setup awaits session-context registration and then permission-evaluate registration before the evaluate callback is available. There is no setup-level catch that can turn a registration failure into a permission `deny`. If setup/registration fails before the evaluate hook is registered, the runtime cannot guarantee interception or blocking; the correct product statement is that the integration is unavailable, not that writes safe-fail. Concrete host feedback is an implementation/validation item; no host signal is claimed established.
- Once the registered callback is invoked, `index.ts:742-765` catches callback/evaluation exceptions and sets `event.effect = 'deny'`. This is source evidence for the registered-hook failure path only, not host-test evidence or proof of interception for unregistered/unexposed operations.
- The optional-plugin case is distinct: when absent/disabled, the core CLI remains usable, but there is no runtime interception guarantee.

## Official V2 Evidence and Implementation Validation Boundary

### Documentation actually inspected

- `https://opencode.ai/v2/docs/build/plugins` documents `Plugin.define`, generic hook registration, session prompt admission, session context, plugin location, and permission `list/get/reply` APIs. It states that `ctx.location` describes where that plugin instance was loaded, not each session's location. The prompt hook mutates the draft into canonical persisted user input, runs at admission rather than each model call, and does **not** expose a typed rejection API. The session context hook changes outgoing model calls, not persisted history. The permission section shows inspect/reply operations, not `ctx.permission.hook('evaluate')` or a mutable permission event effect/message contract. Therefore prompt/context text and plugin location cannot serve as authenticated issuer or repository binding, and source code cannot prove a permission-evaluation hook is supported.
- `https://opencode.ai/v2/docs/permissions` specifies `allow`, `ask`, and `deny`, and says multi-resource operations deny if any resource denies, otherwise ask if any asks. A client may answer `once`, `always`, or `reject`; `always` writes the tool's proposed patterns as a durable project-scoped allow rule. That saved permission is broader/different host state, not a ChangeBudget grant or fresh per-operation issuer event. A ChangeBudget evaluator must independently enforce its scope on each operation; saved `always` must never be treated as grant evidence or a bypass. Host behavior and incoming-event exposure still require testing against the actual installed version.
- Context7 documentation resolution was unavailable due to the monthly quota, so no Context7 claim is made. The two official V2 pages above were used directly; their documented limits do not establish the project-pinned package's exact runtime hook surface.

### Implementation validation requirements (not planning blockers; evidence pending)

1. **Native authority lifecycle.** Implement and prove that agent-invoked ChangeBudget creation/expansion/revocation/rebind through the guarded Runtime Guard path BLOCKS regardless of saved OpenCode `always`/allow. Prove that an agent can only present a minimum proposal and user-facing instructions, and that a human's ChangeBudget-owned native admin action occurs outside governed agent execution. Ordinary host `ask`/`once` must never be accepted as canonical HARD authority. New material HARD authority yields a proposal plus BLOCK pending that separate action.
2. **Local physical binding.** Implement the user-owned registry outside the repository, repo-local public reference, and physical ChangeBudget anchor associated with Git common-dir. Validate shared local domain across linked worktrees with grants still work-bound; unavailable/unreliable physical identity fails HARD binding closed while routine non-HARD operations can continue. Do not add path/remote/copied-UUID fallback. Test unchanged common-dir with changed contents as same instance; same-path replacement only when common-dir instance changes; moves only with verified physical ID; clone/full-copy/cross-machine noninheritance; explicit audited old/new rebind without silent grant migration. Platform validation includes POSIX, Windows file-ID reuse, and OneDrive; no such evidence is claimed by this planning pass.
3. **Installed host interception.** Verify the installed OpenCode/plugin contract, complete resource delivery, before-operation interception, deny/effect behavior, incoming restrictions, and supported integration-unavailable feedback. If hook setup/registration fails before the callback exists, report integration unavailable and do not claim successful blocking. Product decisions and task generation do not depend on live host proof, but implementation conformance does.
4. **Deterministic/runtime cases.** Validate lifecycle and ChangeBudget-owned audit behavior, fail-closed admin paths, mixed/multi-target and out-of-repository resources, pre-init direct-state/unknown CLI behavior, and retry/write failure in disposable repositories. Historical beta.7 is a SEPARATE_RUNTIME_INVESTIGATION. Filesystem tests, multi-target/out-root cases, and the beta.7 observation are implementation validation, not planning blockers. Do not require a live OpenCode once/reject ASK experiment for task generation; any ordinary ASK trace is operational evidence only and cannot establish native authority.

The conceptual grant reference is ChangeBudget-owned and canonical; only the orchestrator receives that identifier. It binds exact paths, capabilities, numeric ceilings, repository/work, authority/schema version, provenance, and lifecycle. The registry is user-local and outside the repository; the repo-local reference is public and not authority on its own. The local threat boundary excludes a malicious unrestricted same-user actor able to tamper with external/repository/anchor/admin paths. No cryptographic federation, OS sandbox, new command name, schema, API, or numeric default is selected here.

Every autonomous authority-consuming operation and native grant administration action must retain structured evidence through ChangeBudget-owned lifecycle handling, not permission evaluation. Audit-write failure must prevent the authority-consuming/admin operation from committing; deterministic deduplication/retry/crash recovery remains implementation design/validation. Existing `materialDecision` hook persistence is a source divergence, not a resolved runtime behavior.

Preserve SPEC-002/003 owner semantics: unresolved material legacy numeric provenance yields the existing completed HUMAN_REVIEW check result when prerequisites pass, while Guardian BLOCKS an operation relying on unresolved authority. Fatal command prerequisites remain fatal. New material HARD authority is not obtained by runtime ASK: present only the minimum user-facing proposal and block the governed operation until a separate native ChangeBudget action is completed. Human-review check output remains distinct from runtime BLOCK.
