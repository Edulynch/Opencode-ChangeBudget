## Decisions

### Native plugin shape

The source proposes `Plugin.define({ id: 'changebudget', setup(ctx) })`; the official V2 guide demonstrates `Plugin.define` generally. This does not validate every source registration against the installed pinned package/host. No older API shape is recognized or translated.

### Hook surface

The source proposes `ctx.session.hook('context', ...)` and `ctx.permission.hook('evaluate', ...)`. Official docs describe session context hooks and generic hooks but do not document the proposed permission-evaluate hook/event/effect contract. Whether it receives every action/resource before execution is a blocking installed-host question; do not assume it from a source call or fixture. No supplemental adapter, pre-execution hook, or correlation map is authorized as a workaround.

### Restrictive aggregation

Project each resource independently, then select the strictest result. The order is `deny > ask > allow`; internal `block` becomes V2 effect `deny`. An incoming restrictive effect is never weakened.

### Unknown and broken context

An uninitialized repository is passive for ordinary non-ChangeBudget operations, subject to the all-state direct `.changebudget/**` block and fail-closed attempted-CLI classification clarified below. An initialized repository with missing/corrupt state, no active contract, or an unresolved mutation target fails safe with a denial. Read-only work remains allowed when it can be classified as read-only.

### Structured material decisions

Existing material-decision input is an explicit structured value that current source reads from permission metadata, normalizes, and passes to existing execution-gate governance. Current source can observe that this particular metadata value is `ABSENT`; that absence MUST NOT be treated as proof that no human premise or ChangeBudget-canonical grant exists. Do not invent an assumption that canonical grant evidence is always present in this metadata slot, or that prose/transport alone issues a grant. No ordinary request fabricates a material proposal. The product constraint is that permission-hook evaluation must not persist approvals or lifecycle evidence; current source has a valid-material-decision path that may persist a governance ledger, recorded below as a PENDING divergence from that constraint. Authority provenance and requirements are planning design and no new metadata shape is proposed.

### Local-first behavior

The intended integration reads local state and makes no network calls or plugin-owned permission-hook writes; lifecycle evidence belongs to ChangeBudget-owned lifecycle handling. Current source's material-decision path may write a governance ledger during evaluation, so the no-hook-write invariant is not currently met. The core CLI remains independent when the plugin is unavailable.

## Clarification and traceability (2026-09-24)

### Prior #41 CLI projection — historical and obsolete as a universal ask rule

The user direction keeps a distinction between direct state mutation and recognized ChangeBudget CLI lifecycle operations, but the earlier one-ask-per-recognized-mutation projection is **OBSOLETE — REQUIRES REVISION**. #41/beta.7 is historical evidence of a static classifier and its previous asks, not a Guardian V2 policy approval or implementation.

- Direct writes to `.changebudget/**` remain blocked in every repository state, including before initialization and with no active contract.
- Lifecycle autonomy is available only through a recognized ChangeBudget CLI invocation. `start`, a minimally grant-covered `amend`, normal `close` after `PASS`, and the other enumerated cases follow `spec.md` conditions. This is not a claim of current runtime effects or conformance.
- The prior static classifier called `init`, `start`, `amend`, `close`, non-dry-run `integrate`, satisfaction-evidence `check`, external `update`, and `close --force` mutating CLI forms. Its former universal ask mapping is not binding. Product conditions for these lifecycle cases are resolved in `spec.md`; exact existing-input-to-runtime projection is planning design.
- The former read-only examples were `status`, `diagnose`, help/version, `check` without satisfaction evidence, `update --check`, and `integrate opencode --dry-run`. These are classifier examples, not proof of consistent host behavior; preserve the beta.7 discrepancy below.
- Unknown/malformed CLI syntax, invalid evidence, shell control operators around an attempted ChangeBudget invocation, and unrecognized wrappers for such an invocation remain fail-closed requirements in every repository state. Absolute executable paths require verified identity as a shim for the installed ChangeBudget package; a name/string match alone is insufficient. This is not a claim that every Windows wrapper is supported.
- If a future mapping selects `ask`, it remains one-invocation only and cannot authorize direct `.changebudget/**` edits or persist/widen policy. This conditional semantic does not preserve the obsolete ask-per-operation trigger.

The current projection source does not fully meet the direct-state requirement: `opencode-plugin/src/projection.ts` returns passive allow at approximately lines 88-95 before checking `targetInChangeBudget` at approximately lines 156-163. The all-state direct-state prohibition and unknown attempted-CLI fail-closed requirement remain normative; these source-order mismatches are implementation gaps, not policy exceptions, and are PENDING remediation and regression evidence. ### Guardian V2 product and cross-spec audit (2026-09-24)

- Preserve the exact explicit human premise, including Docker + Redis Cluster + three instances. Reduce optional implementation delta, not the goal; do not add optional tests/refactors/infrastructure. REFOCUS rejects an oversized solution, not the task, and precedes escalation; it is a workflow concept, not runtime action, command, exit code, API, or schema.
- Soft planner/agent `expected_files`/`expected_changed_lines` concepts warn of drift and alone do not ask or block. `max_files`/`max_changed_lines` are hard only with verifiable human/policy provenance; exceeding a qualified hard ceiling requires new authority. The owner semantics are aligned in SPEC-002 `spec.md` FR-009/FR-010/FR-021 and SPEC-003 `spec.md` FR-002/FR-003/FR-004/FR-007. SPEC-002 FR-021 defines the deterministic legacy rule: exact human ceiling intent or trusted exact policy provenance is HARD; a verifiable unadopted recommendation is SOFT; unknown/ambiguous origin or intent is UNRESOLVED, with HUMAN_REVIEW when material to safe evaluation and no inferred hard violation. Legacy contracts remain readable without schema migration. SPEC-002 FR-011 allow-list and FR-012 hard-deny semantics remain owned there.
- `REPAIR` alone is not a stop or authority grant: current-authority repair continues with minimum delta, valid grant-covered amendments continue with minimum delta, independently verified optional work may REFOCUS, proven new authority ASKs, and invalid/unsafe work BLOCKS. When optionality is unverified, a covered concrete operation still CONTINUES; lack of an optionality signal is not an authority failure. `HUMAN_REVIEW` is not authority; its reasons distinguish optional/REFOCUS, new authority/ASK, and invalid/unsafe/BLOCK.
- Authority-delta minimality is explicit: current 18, ceiling 60, one-file requirement → 18→19, not 18→60; a sufficient exact path `src/foo.ts` does not broaden to `src/**`. Minimality is authority delta, not an architectural-necessity proof.
- Authority distinguishes trusted human intent, a ChangeBudget-canonical structured grant, and a verified human authorization event; the orchestrator may consume/reference but not issue a grant. EvoSpec/other transport carries only previously granted authority and cannot issue/expand it. Prefer an id/reference without naming a schema. Bind repository, work/task, authority/schema version, and lifecycle status. Invalid/malformed/forged/cross-repo/cross-task/revoked/expired/consumed/stale authority BLOCKS. A grant reported consumed blocks when presented; stage-to-stage reuse in one active bounded START→AMEND→REPAIR→CLOSE lifecycle is not consumed replay. After successful CLOSE it cannot replay for unrelated work.

Lifecycle rules: `start` may proceed autonomously when premise/valid grant suffices and uses narrow requested values, never maximum grant ceilings. Clean first-time `init` is autonomous only for an eligible repo without conflicting ChangeBudget state or protected/pre-existing overwrite conflict when covered by an authenticated direct setup request or a verified parent premise for the bounded work; no separate exact-init request is required and a raw CLI invocation alone proves nothing. CLI init is separate from direct state writes, which always block. A grant-covered minimal `amend` continues; normal `close` after PASS and required completion is autonomous. Force close/bypass may preflight-ASK for exact fresh approval only through a verified human channel; do not execute until that event is retained. Without it, an actual force execution attempt blocks/is unavailable, and it never permits direct protected writes. `integrate opencode --dry-run`, `update --check`, and a proven-owned wrapper refresh are autonomous. Real integration requires explicit human setup/integration request; real package update requires explicit user update request and is not background coding. Explicitly requested sensitive categories do not cause redundant category-only asks; novel expansion is authority-evaluated.

MVP retains ChangeBudget-owned structured evidence for every autonomous authority-consuming operation: requested operation, current authority, grant/premise coverage, minimal delta, subset/boundary checks, no-prompt rationale, and any REFOCUS/ASK/BLOCK decision and reason. This supersedes the old no-audit clarification without prescribing a store or making hook evaluation persist it. Product decisions are internally aligned, but planning remains NEEDS_CLARIFICATION until the issuer, repository-binding, and installed-hook evidence gates are closed. No final fields, API, schema, lifecycle representation, REFOCUS command/exit code, or reason codes are inferred.

MVP includes soft/hard provenance, covered START, canonical grants, minimum numeric/exact-path AMEND, within-authority REPAIR, REFOCUS, normal CLOSE, all-state direct protection, repository/work binding, replay/staleness, and audit evidence. Explicit deferrals are cloud/distributed authorization, arbitrary third-party issuers, organization grants, cryptographic federation, and LLM compliance as enforcement authority.

### Hook availability versus evaluation failure — source inspection only

- In `opencode-plugin/src/index.ts:730-742`, setup awaits session-context registration and then permission-evaluate registration before the evaluate callback is available. There is no setup-level catch that can turn a registration failure into a permission `deny`. If setup/registration fails before the evaluate hook is registered, the runtime cannot guarantee interception or blocking; the correct product statement is that the integration is unavailable, not that writes safe-fail. Concrete host feedback is an implementation/validation item; no host signal is claimed established.
- Once the registered callback is invoked, `index.ts:742-765` catches callback/evaluation exceptions and sets `event.effect = 'deny'`. This is source evidence for the registered-hook failure path only, not host-test evidence or proof of interception for unregistered/unexposed operations.
- The optional-plugin case is distinct: when absent/disabled, the core CLI remains usable, but there is no runtime interception guarantee.

## Official V2 Evidence and Unresolved Trust Gates

### Documentation actually inspected

- `https://opencode.ai/v2/docs/build/plugins` documents `Plugin.define`, generic hook registration, session prompt admission, session context, plugin location, and permission `list/get/reply` APIs. It states that `ctx.location` describes where that plugin instance was loaded, not each session's location. The prompt hook mutates the draft into canonical persisted user input, runs at admission rather than each model call, and does **not** expose a typed rejection API. The session context hook changes outgoing model calls, not persisted history. The permission section shows inspect/reply operations, not `ctx.permission.hook('evaluate')` or a mutable permission event effect/message contract. Therefore prompt/context text and plugin location cannot serve as authenticated issuer or repository binding, and source code cannot prove a permission-evaluation hook is supported.
- `https://opencode.ai/v2/docs/permissions` specifies `allow`, `ask`, and `deny`, and says multi-resource operations deny if any resource denies, otherwise ask if any asks. A client may answer `once`, `always`, or `reject`; `always` writes the tool's proposed patterns as a durable project-scoped allow rule. That saved permission is broader/different host state, not a ChangeBudget grant or fresh per-operation issuer event. A ChangeBudget evaluator must independently enforce its scope on each operation; saved `always` must never be treated as grant evidence or a bypass. Host behavior and incoming-event exposure still require testing against the actual installed version.
- Context7 documentation resolution was unavailable due to the monthly quota, so no Context7 claim is made. The two official V2 pages above were used directly; their documented limits do not establish the project-pinned package's exact runtime hook surface.

### Minimum model and decision consequences

The minimal conditional choice is the ChangeBudget-generated contract ID as a bounded work ID, with `task_id` only optional SpecKit correlation, existing draft/active/closed lifecycle, and a ChangeBudget-owned authorization event linked to the draft before activation. A grant is only an opaque reference to that evidence. Use existing history if it can verify both pre-start issuer evidence and all subsequent operation evidence; otherwise evaluate only a minimal local event/journal associated with the contract. No global registry, standalone grant database, token service, final schema, or storage path is approved here. The candidate local repo tuple and its limitations are set out above.

Every autonomous authority-consuming operation must append structured evidence through a ChangeBudget-owned lifecycle transaction, never from permission evaluation. Write failure means no operation commit; deterministic deduplication/retry/crash recovery must be specified before implementation. A material decision currently reaches `evaluateAndRecordMaterialDecisionInPlace` through the permission evaluator, a concrete source divergence from the no-hook-side-effect rule.

Do not ask for a category merely because it is sensitive; do not infer a required operation from a speculative proposal. The pending exact operation or deterministic Git changed set must prove its concrete paths/metrics. Deny/protected precedence and full-resource subset checks apply. Independent orchestration owns semantic intent/optionality; REFOCUS only follows a separately verifiable optional-proposal signal within bounded trusted work and has no permission effect. If the signal is untrusted or absent, continue any concrete operation already within valid authority; do not infer an authority failure. ASK only for a demonstrably uncovered minimum when the issuer channel is verified; with no channel, do not execute or mint authority and surface approval as unavailable. BLOCK only an actually unknown/unsafe target or authority relied upon. Human-review check output remains distinct from runtime BLOCK as specified in SPEC-002/003.
