## Planning guardrails

- Preserve the exact user-requested outcome. Minimize implementation and authority delta, not the outcome. Do not add optional tests, refactors, dependencies, infrastructure, product semantics, new authority models, public APIs, arbitrary/prescriptive storage designs, command names, reason-code families, or numeric defaults. Minimal additive, backward-readable internal persistence for provenance, audit, or repository binding is permitted when directly required by the approved task and authorized in its exact execution contract; it must not become a new public schema/API or plugin-owned audit store.
- HARD authority is distinct from human intent and a verified ChangeBudget-native authorization event. A user-facing minimum proposal plus BLOCK is not OpenCode ASK. OpenCode `ask`/`once`/`always` is operational only and cannot mint, expand, rebind, or substitute for HARD authority.
- Agent-path canonical grant create/expand/revoke/rebind MUST BLOCK even under saved host allow/always. Human ChangeBudget administration occurs outside governed agent execution. Force CLOSE is separately gated by fresh native authorization; host permission is not that authorization.
- Repository binding is local: user-owned registry outside the repository, repo-local public reference, physical ChangeBudget anchor associated with Git common-dir. The unchanged common-dir instance stays the same despite working-content changes; linked worktrees share repository identity but not work grants. HARD binding fails closed if genuine physical identity is unavailable or unreliable. No path, remote, copied UUID, or silent rebind fallback.
- Preserve SPEC-002/003 ownership: soft estimates are advisory; provenance-qualified hard ceilings are enforceable; ambiguous legacy provenance is UNRESOLVED. Preserve allow-list/hard-deny semantics and fatal prerequisites. No fabricated PASS or retroactive grant.
- Audit belongs to ChangeBudget-owned lifecycle handling; it is required before an authority-consuming/admin operation commits. Permission-hook evaluation MUST NOT persist audit evidence. Establish the write/commit barrier before enabling lifecycle behavior that consumes authority.
- No cloud/distributed authorization, arbitrary third-party or organization issuer, cryptographic federation, OS sandbox/security claim, or LLM judgment as enforcement authority. Do not assume host-hook support, all-resource delivery, native issuer proof, or reliable file IDs; validate them before claiming support.
- “Depends on” is the complete task DAG. Task numbers are new and unique; `[ ]` means pending. Every task names the affected subsystem, applicable normative requirements, dependencies, and test/acceptance evidence. Source/test paths identify candidate ownership and evidence, not current behavior claims.

- Foundation: `GV2-001 → GV2-002 → GV2-003`; repository branch `GV2-001 → GV2-002 → GV2-004 → GV2-005 → GV2-006` joins the audit/read-only branch at `GV2-007`.
