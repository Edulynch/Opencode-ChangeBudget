# Implementation Plan: OpenCode V2 Runtime Guard

> Status: Draft — **NEEDS_CLARIFICATION**. Owner semantics are aligned with SPEC-002/003, but three evidence gates are not verified: an authenticated human authorization source, a dependable local repository binding, and the actual installed host's permission-hook contract. This plan is conditional and is not READY_FOR_TASKS, an implementation baseline, or evidence that tests/host checks passed. Source/test references are evidence locations only.

## Summary

SPEC-004 is intended to preserve the requested outcome while guarding authority and unsafe operations at the OpenCode V2 boundary. The existing policy results remain `PASS`, `REPAIR`, and `HUMAN_REVIEW`; the existing runtime vocabulary is `allow`, `ask`, and internal `block` (mapped to `allow`, `ask`, or `deny`). Guardian V2's product ordering is resolved; mapping the existing inputs to the product rules is implementation planning. `REFOCUS` is a workflow concept, not a runtime effect or new enum.

The implementation is an optional plugin package. The ChangeBudget CLI remains usable when OpenCode is absent or the wrapper is not installed.

## Product Direction and Planning Gate

Product decisions in `spec.md` are resolved for planning. Preserve the exact direct-human requested outcome; minimize implementation/authority delta only; do not add optional tests, refactors, or infrastructure. A premise is trusted intent but not unlimited structured authority. Keep it distinct from a ChangeBudget-canonical structured grant and the verified human authorization event that establishes it. An orchestrator can consume/reference a grant, never issue one; EvoSpec/other transport can only carry/reference prior grants. Bind authority to repository identity, work/task identity, authority/schema version, and lifecycle status. Invalid, forged, cross-repository/task, revoked, expired, reported-consumed, or stale authority blocks rather than prompting again; valid stage-to-stage use within one active bounded START→AMEND→REPAIR→CLOSE lifecycle is not consumed replay. A valid grant cannot authorize unrelated work after successful close.

Planner/agent expected file/line counts are soft drift estimates. Existing `max_files`/`max_changed_lines` are hard ceilings only with human/policy provenance; estimate overage alone is not ASK/BLOCK, and hard-ceiling overage requires new authority. These owner semantics are now normative in SPEC-002 `spec.md` FR-009/FR-010/FR-021 and SPEC-003 `spec.md` FR-002/FR-003/FR-004/FR-007. SPEC-002 FR-021 classifies legacy values as HARD only with verifiable exact authority and ceiling intent, SOFT when they are verifiable unadopted recommendations, and UNRESOLVED when origin/intent is ambiguous; material unresolved provenance is HUMAN_REVIEW at check and blocks Guardian operations relying on that authority. SPEC-002 FR-011 allow-list and FR-012 hard-deny semantics remain owned there; a path mismatch alone is not a universal ASK, and no denied/protected path is authorized. Implementation representation and recovery workflow remain planning items; no owner schema or migration was introduced.

The authority-delta examples are normative: with current 18 and ceiling 60, one more required file asks for/authorizes 18→19 rather than the full ceiling; where an exact valid path grant suffices, amend `src/foo.ts`, not `src/**`. Minimality is measured as the authority delta, not an architectural necessity proof.

Apply this response order: preserve premise; CONTINUE within current authority; use minimum mechanically implied concrete delta; use minimum concrete delta covered by a valid grant; REFOCUS optional/oversized approaches only when optionality is independently verified, continuing already-covered operations if the optionality signal is untrusted/absent; ASK for only materially new authority; BLOCK invalid authorization, unsafe/unknown/protected work, and an actual force/bypass execution attempt without fresh explicit human approval. If an uncovered minimum is proven but no verified fresh approval channel exists, do not execute or mint authority and surface approval as unavailable. A `REPAIR` result is not a blanket stop. `HUMAN_REVIEW` reasons distinguish verified optional expansion→REFOCUS, genuine new authority→ASK, and invalid/unsafe authority or state→BLOCK. Sensitive work named in the premise does not trigger a redundant ask solely by category; novel expansion is authority-evaluated. Preserve separately gated protected-path and force rules. No final code/reason names are set.

Lifecycle and integration product rules: clean first-time CLI `init` may be autonomous for an eligible repository with no conflicting ChangeBudget state or protected/pre-existing overwrite conflict when an authenticated direct setup request or an existing verified parent premise for the bounded work covers necessary initialization; it does not require a separate exact-init request, and a raw CLI invocation alone is not authorization. This never permits direct `.changebudget/**` writes. `start` is autonomous when the premise/valid grant already covers it and creates narrow requested contract values, never grant ceilings as a template. A minimum grant-covered `amend` continues. Normal `close` after `PASS` and required completion conditions is autonomous. Force close/bypass may preflight-ASK for the exact fresh approval only through a verified human channel; no pending force operation executes before the exact event is validated and retained. An actual force execution attempt without approval, after rejection/stale approval, or with an unavailable/unverified approval channel BLOCKS/is unavailable. A generic host ask or saved `always` rule is not approval. Fresh approval covers only that one force operation, never direct protected writes. `integrate opencode --dry-run`, `update --check`, and a proven-owned wrapper refresh may be autonomous; real integration requires an explicit human setup/integration request, while a real package update requires an explicit user update request and is not background coding. These are product conditions, not an invented command/state/exit code or final plugin projection.

Retain structured ChangeBudget-owned evidence for every autonomous authority-consuming operation: requested operation, current authority, grant/human-premise coverage, minimal delta, subset/boundary checks, rationale for no prompt, and any REFOCUS/ASK/BLOCK decision and reason. This supersedes the historical no-audit clarification for MVP. Do not prescribe a store or persist from the permission hook; do not claim the current code implements evidence capture.

MVP includes soft/hard provenance, covered START, canonical grants, minimum numeric/exact-path AMEND, within-authority REPAIR, REFOCUS, normal CLOSE, all-state direct-state protection, repo/work binding, replay/staleness, and structured evidence. Defer cloud/distributed authorization, arbitrary third-party issuers, organization grants, cryptographic federation, and LLM compliance judgments as enforcement authority.

**Planning readiness:** the product ordering and SPEC-002/003 numeric-provenance/decision semantics are internally aligned, but implementation planning is **NEEDS_CLARIFICATION** until the three trust gates below have affirmative, recorded evidence. A coherent conceptual model does not satisfy those gates. Do not claim READY_FOR_TASKS or begin implementation based solely on this plan. The reviewer-owned checklist remains incomplete and is not automatic signoff.

## Conditional Implementation Plan and Evidence Gates

This is an ordered plan, not a generated task list. Each later phase depends on every earlier gate passing. If a gate cannot be evidenced using supported, installed behavior without inventing an issuer, host API, or identity guarantee, stop at NEEDS_CLARIFICATION and return for clarification. Do not resolve a failed gate by adding a new service, global registry, database, token system, scheduler, IPC layer, or runtime-LLM authority.

### Phase 0 — Verify the trust boundary (blocking prerequisite)

1. **Authenticated human/policy issuer:** establish which installed, supported admission/approval event proves that a human supplied the direct premise and separately approved structured scope; identify the trusted exact policy source if policy provenance is used. Record actor/source, exact accepted text/scope, one-operation or grant decision, and stable correlation to the ChangeBudget transaction. Arbitrary flags, a user-looking prompt string, plugin metadata, an orchestrator/model, session memory, saved permission rules, and `materialDecision` metadata are not proof. Current official docs do not establish an authenticated human issuer or typed rejection/approval surface, and no trusted policy event source is evidenced here; until an authorized evidence source does, no grant or policy-derived hard ceiling may be attributed and the gate fails.
2. **Local repository binding:** verify a deterministic local binding candidate from the canonical Git worktree root and Git common directory plus a ChangeBudget init-local identity, checked against the current repository for every use. The current lifecycle state has no repository ID and the Git helper returns only a top-level root; the added ChangeBudget identity is not implemented. Define and evidence path canonicalization across Windows/POSIX, symlink/case behavior, worktrees, clones, moves, same-path replacement, and copied `.changebudget` state. A path/root tuple is not cryptographic identity. If copied or replaced state can be mistaken for its original authority under the declared threat model, binding remains unresolved rather than being described as guaranteed.
3. **Actual installed host hook:** identify the installed OpenCode version and plugin package/types, then prove that the registered permission-evaluation hook is supported, invoked before the covered operation, receives the complete action/resource set, and that its effect/message changes the pending operation. Also establish the supported unavailable signal if registration fails. The official V2 guide inspected documents generic hooks, session prompt/context hooks, and permission list/get/reply, but does not document the proposed permission `evaluate` hook/effect/message contract; pinned installed declarations were unavailable in the bounded inspection. The beta.7 observations remain contradictory and the failed host's action/resources are missing.

### Phase 1 — Finalize the smallest local evidence representation (only after Phase 0)

Reuse one ChangeBudget-minted `ChangeContract.id` as the bounded work identity; keep optional `task_id` solely as SpecKit correlation. Preserve existing draft/active/closed lifecycle status. Because no active contract exists before `START`, create/use a draft identity and retain the verified human/policy authorization event linked to that draft **before activation or any authorized mutation**. A grant is an opaque reference to this ChangeBudget-owned evidence, not a bearer string issued by an orchestrator. A different task/work item gets a different contract ID.

Do not create a standalone global grant registry. First determine whether existing ChangeBudget-owned contract/lifecycle history can retain and validate (i) pre-start verified issuer evidence and (ii) subsequent operation evidence. Existing contract values, amendment lists, execution-envelope JSON, permission metadata, or a post-hoc snapshot are insufficient by themselves to prove issuer and event provenance. If those histories cannot do both, propose only the minimum local journal/event record associated with the draft/contract; decide atomicity, deduplication, and recovery in design review. No final field names, schema, persistence path, or public API are selected in these planning artifacts.

The conceptual evidence binds the verified issuer/source and exact authorization event; current repository binding; contract/work identity; authority/schema version; normalized operation, paths, numeric limits and capabilities; provenance class; lifecycle status; and an opaque reference. Numeric evidence follows SPEC-002 FR-021: HARD only for verified exact human ceiling intent or trusted exact policy provenance, SOFT for verified unadopted recommendations, and UNRESOLVED for ambiguous provenance. Never upgrade a legacy value or treat prose alone as structured path/capability authority.

### Phase 2 — Define lifecycle transaction and fail-closed persistence

The verified evidence is established before `START`; grant validity persists only through its matching active `START→AMEND→REPAIR→CLOSE` lifecycle. Validate repository/work/version/status and revocation/staleness before each operation. The authorized operation's complete proposed target set, measured/pending metrics, and capabilities must be a subset of currently authorized union, after deny/protected precedence. Unknown, unrepresentable, out-of-repository, mixed-resource, or protected targets fail closed. Close is terminal for unrelated reuse; clones/moves/replacements require reauthorization when binding cannot be verified.

Every autonomous authority-consuming operation must retain structured ChangeBudget-owned evidence in the lifecycle transaction: operation and all targets; prior/current authority and provenance-event reference; repository/work/version/status; minimum delta and subset/boundary result; the deterministic basis for coverage/no prompt; result; and any REFOCUS/ASK/BLOCK reason. Permission-hook evaluation must not write the ledger. If the lifecycle/audit write fails, the authority-consuming operation does not commit. Specify deterministic request identity, deduplication, and recovery for retries/crashes before implementation: duplicate delivery cannot widen or apply authority twice, and an ambiguous partial write must stop for reconciliation rather than be treated as success. Do not claim filesystem multi-file atomicity without proof.

### Phase 3 — Map the response sequence and lifecycle cases

Preserve incoming restrictive effects; evaluate all resources and aggregate `deny > ask > allow`; never let a saved host `always` approval substitute for ChangeBudget verification. Continue within a valid grant and use the smallest currently covered delta. Derive a concrete required operation from the pending exact operation or deterministic Git changed set, not speculative proposals. Do not prove architecture necessity or use an LLM judgment. The independent executor/orchestrator owns semantic intent and optionality; Guardian may REFOCUS only when an optional proposal signal is independently verifiable within trusted bounded work. An untrusted or absent optionality signal only prevents REFOCUS: if the concrete pending operation is within current valid authority, CONTINUE; lack of optionality proof alone does not make that authority unknown and does not trigger ASK/BLOCK. Numeric drift or untrusted metadata alone cannot prove optionality or authority failure. REFOCUS denies only the proposed optional mutation with structured feedback; any session-context text is advisory for a later request and gives no authority. ASK only for a separately proven uncovered minimum delta when a verified fresh human response can be captured; without that channel, do not execute or mint authority and surface approval as unavailable. BLOCK only when the target is unsafe/unresolvable or the authority actually relied upon is invalid/unknown. For force close/bypass, preflight may ASK for the exact fresh approval through a verified human channel; do not execute while pending, and BLOCK/unavailable if approval is rejected/stale or the channel cannot be verified. A host `ask` or saved `always` alone is not that human event. Keep this sequence separate from `PASS`/`REPAIR`/`HUMAN_REVIEW` reporting as detailed in the runtime decision contract.

Multi-target protection and out-of-repository target handling are source-inspection suspicions, not reproduced defects. Do not port the obsolete universal ASK or `REPAIR`/`HUMAN_REVIEW` block as a repair strategy.
